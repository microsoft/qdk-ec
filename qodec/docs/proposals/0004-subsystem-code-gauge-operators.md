# 0004 - Subsystem-code gauge operators

**Status:** proposed

## Context

Consider a four-qubit Bacon-Shor code with one protected logical qubit and one
unprotected qubit. A syndrome-extraction circuit measures $X_0X_2$ and
$X_1X_3$. Their product is the stabilizer $X_0X_1X_2X_3$, but neither individual
measurement has to return a fixed sign.

The unprotected qubit is the **gauge subsystem**: operations may change its
state while preserving the protected logical state.

### The four-qubit example

Use stabilizers $X_0X_1X_2X_3$ and $Z_0Z_1Z_2Z_3$, with protected logical
operators $\bar X=X_0X_1$ and $\bar Z=Z_0Z_2$.

The X measurements above commute. Likewise, $Z_0Z_1$ and $Z_2Z_3$ commute and
reveal the Z stabilizer through their product. An X gauge measurement and an
overlapping Z gauge measurement can anticommute; neither is a stabilizer whose
sign must remain fixed throughout the schedule.

The current [Code](../../src/code.rs) declares stabilizers and protected logical
`x`/`z` operators. Gadget [references](../../src/parity.rs) address those families,
but not gauges. A circuit can measure the Paulis in this example and combine
their bits into checks. It cannot declare the measured operators as part of a
gauge subsystem shared by the code and its gadgets.


Treating a gauge operator as a stabilizer would require a fixed sign that the
protocol does not promise. Treating the gauge qubit as another protected qubit
would require gadgets to preserve information they may discard. A code-level
gauge declaration lets an analysis tool distinguish those freedoms from an
actual logical error, across different implementations of the same code.

## Benefits

- Check logical correctness without rejecting harmless changes to the gauge state.

## Drawbacks

- Gauge signs depend on the measurement schedule; incompatible gauges do not
  have simultaneous definite signs.
- A paired basis may not match the generators measured by hardware.
- Code dimensions and analysis tools must distinguish gauge and protected qubits.

## Proposal

Evaluate two optional ordered lists on `Code`, `gauge_x` and `gauge_z`, with one
paired entry per gauge qubit. The full gauge group is generated by these pairs
**together with the stabilizers**; the pairs alone need not generate the center.
The following is proposed syntax for the example above:

```yaml
name: bacon_shor_2x2
stabilizers: [X_0 X_1 X_2 X_3, Z_0 Z_1 Z_2 Z_3]
x: [X_0 X_1]
z: [Z_0 Z_2]
gauge_x: [X_0 X_2]
gauge_z: [Z_0 Z_1]
```

There are two independent stabilizers, one protected logical qubit, and one
gauge qubit: $n=s+k+r=2+1+1=4$. The omitted measured generators follow from
products with the stabilizers: $X_1X_3=S_Xg_X$ and $Z_2Z_3=S_Zg_Z$.

### Code and reference semantics

- Entry `i` in each gauge list is the same zero-based gauge-qubit index.
  These are lists of operators, not maps from arbitrary labels. Equal lengths
  are required for a valid complete paired basis; audit may report an incomplete
  declaration without making the draft impossible to preserve.
- `x` and `z` continue to name protected logical operators. Gauge operators do
  not increase the instruction's protected logical arity.
- Paired gauge generators anticommute within each pair and commute across
  distinct pairs. They commute with the declared stabilizers and protected
  logical representatives. The gauge group has the declared stabilizer group
  as its center, modulo scalar phases, for a complete valid declaration.
- Dimension inference must include gauge operators when determining physical
  support and expose the distinction between $k$ and $r$ to consumers.
- Explore parity references such as `in[0].gauge_x[0]` and
  `out[0].gauge_z[0]`, but only with an explicit rule for when a gauge sign is
  available. The first index selects a boundary encoding; the final index
  selects its gauge operator. Declaring an operator does not assert sign +1.

For example, after preparing or measuring the X gauge and before an
anticommuting gauge operation, a subsequent X measurement may be related to its
established sign. A Z-gauge measurement generally invalidates that X-sign
knowledge. A check against an arbitrary input gauge sign is not automatically
a deterministic-zero check. Consumer analysis must track these preconditions.

## Alternatives

- Keep only the circuit measurements: no new code fields, but no declaration
  of which encoded state is unprotected.
- Fix gauges as extra stabilizers: describes a chosen gauge state, not an
  arbitrary one, and may require different codes at different stages.
- Store a flat list of measured generators: preserves hardware choices, while
  consumers derive a paired basis if needed.
- Store both lists: explicit, but they must remain consistent.

## Discussion

### Names and scope

Two fields are proposed: `gauge_x` and `gauge_z`, parallel to logical `x` and `z`.
`gauges` would leave pairing implicit; `gauge_partners` would lose the X/Z
correspondence. The suffixes name symplectic partners, not necessarily pure-X
or pure-Z physical operators. Further accessors are unspecified.

Audit needs commutation, rank, center, and logical/gauge independence checks.
Gauge-sign references additionally need schedule analysis: an unavailable sign
is an error, not zero. Sampled gauge values do not belong in `Code`.

Input and output codes could describe gauge fixing by changing which constraints
are fixed. The declaration does not itself prove that a gadget preserves the
protected action. That requires a subsystem-aware consumer.

Absent gauge fields retain the current code interpretation. Update dimensions,
schemas, bindings, and reference support together under the shared compatibility
and loading rules.

## Open Questions

- Should authors supply paired generators, measured generators, or both?
  Evaluate the paired sketch against a real Bacon-Shor schedule before choosing.
- Is an explicit gauge-qubit count useful, or should analysis derive it?
- Which boundary gauge signs can be referenced, and how is their availability
  established without treating noncommuting observables as simultaneous bits?
- Can the initial feature stop at code declarations and consumer analysis,
  adding gauge-sign references only when a composition use case requires them?
- How should gauge fixing be expressed across input and output code boundaries?
- Which consumer will demonstrate preservation of the protected subsystem while
  permitting changes to the gauge subsystem?
